# ZeroMQ / ZMTP 规范覆盖对照表

本文件详细列出 `moon-zmq` 对 ZeroMQ 官方 RFC 及相关规范的对标与实现覆盖情况。

---

## 一、规范覆盖总览

| 规范编号 | 规范名称 | 覆盖状态 | 说明 |
| :--- | :--- | :---: | :--- |
| **RFC 23** | ZMTP 3.1（ZeroMQ 消息传输协议核心） | **已完成** | 完整支持帧格式、版本协商、NULL 机制、命令帧、大消息与元数据交互。 |
| **RFC 24** | PLAIN 安全机制 | **已完成** | 完整支持客户端/服务端 HELLO / WELCOME / INITIATE 握手及 ZAP 认证回调。 |
| **RFC 25** | CURVE 安全机制 | **不做** | 经深度调研，MoonBit 生态目前暂未提供经过安全审计的 Curve25519 与 XSalsa20-Poly1305 官方密码学库。遵循密码工程与安全规范，本库不临时自制拼凑非标准密码实现；架构层已预留安全机制扩展槽。 |
| **RFC 28** | REQ / REP 请求应答模式 | **已完成** | 严格交替状态机校验、请求应答空帧信封（Empty Delimiter）自动封装与解包。 |
| **RFC 29** | PUB / SUB 发布订阅模式 | **已完成** | 支持多主题订阅、取消订阅、前缀匹配过滤与多端点广播投递。 |
| **RFC 30** | PIPELINE（PUSH / PULL）管道模式 | **已完成** | 支持 PUSH 端公平轮询（Round-Robin）分发与 PULL 端公平接收（Fair-Queuing）。 |
| **RFC 31** | ROUTER 套接字模式 | **已完成** | 异步多路复用、源节点 Identity 信封自动前缀附加、目标寻址投递与强制路由模式。 |
| **RFC 32** | DEALER 套接字模式 | **已完成** | 全双工异步点对点轮询负载分发与接收。 |
| **RFC 47** | XPUB / XSUB 扩展发布订阅模式 | **已完成** | 支持订阅/取消订阅消息向上游透明转发，满足构建发布订阅代理（Proxy/Broker）需求。 |
| **N/A** | PAIR 点对点独占模式 | **已完成** | 独占双向通道，无额外信封与多路路由开销。 |

## 二、逐项详细覆盖对照

### 1. RFC 23: ZMTP 3.1 传输协议核心
- **帧编解码 (Frame Codec)**:
  - 短帧格式（`FLAG(1B) + LENGTH(1B) + BODY`）：**已完成**
  - 长帧格式（`FLAG(1B) + LENGTH(8B, Big-Endian) + BODY`）：**已完成**
  - `MORE` 标志位多帧（Multipart）拼接与切分：**已完成**
  - `COMMAND` 标志位命令帧编码与解析：**已完成**
  - 流式解码状态机（半包暂存、粘包切分、边界恢复）：**已完成**
  - 非法帧头、负长度以及超大帧溢出检测与防护：**已完成**
- **问候帧协商 (Greeting)**:
  - 64 字节标准 Greeting 序列化与反序列化：**已完成**
  - 版本协商（主版本 `3`，次版本 `1`，向下兼容协商）：**已完成**
  - 安全机制标识（`NULL`、`PLAIN` 等，填充对齐至 20 字节）：**已完成**
  - `as-server` 角色位协商与双向一致性检查：**已完成**
- **握手与命令交互 (Handshake & Commands)**:
  - `READY` 命令帧编码与解码（含键值对元数据）：**已完成**
  - `ERROR` 命令帧编码与错误原因传递：**已完成**
  - `SUBSCRIBE` / `CANCEL` 命令交互：**已完成**
  - `PING` / `PONG` 心跳活性探测交互：**已完成**
  - 元数据属性规范（`Socket-Type`、`Identity`）：**已完成**
  - 套接字配对兼容性规则校验（如 REQ 仅匹配 REP/ROUTER 等）：**已完成**

### 2. RFC 24: PLAIN 安全机制
- **认证交互时序**:
  - 客户端向服务端发起 `HELLO` 命令帧（含用户名和密码）：**已完成**
  - 服务端向客户端响应 `WELCOME` 命令帧（认证通过）：**已完成**
  - 认证失败场景下服务端发送 `ERROR` 命令帧并安全关闭连接：**已完成**
  - 客户端发送 `INITIATE` 命令帧交换客户端元数据：**已完成**
  - 服务端响应 `READY` 命令帧完成最终会话建立：**已完成**
- **ZAP (ZeroMQ Authentication Protocol) 机制**:
  - 提供服务端认证回调处理器（`set_plain_server(true, authenticator=...)`），支持应用层自定义用户名密码验证：**已完成**

### 3. RFC 25: CURVE 安全机制
- **状态评估与未实现说明**:
  - **调研结论**：CURVE 安全机制强制依赖 Curve25519 椭圆曲线密钥交换、Ed25519 签名以及 XSalsa20-Poly1305 认证加密算法。经过对 MoonBit 生态及官方包管理体系的全面检索，目前尚无经工业级审计的纯 MoonBit 密码学实现。
  - **决策**：严格遵循信息安全与密码工程的最佳实践，杜绝随意拼凑未经验证的算法实现。本库将 CURVE 标记为后续规划，待 MoonBit 官方密码学库完备后，依托预留的安全机制接口无缝升级支持。

### 4. RFC 28: REQ / REP 套接字模式
- **严格交替状态机**:
  - `REQ` 必须遵循先 `send` 后 `recv` 的交替序列，连续两次 `send` 将引发 `InvalidState` 错误：**已完成**
  - `REP` 必须遵循先 `recv` 后 `send` 的交替序列，在接收到请求前禁止调用 `send`：**已完成**
- **信封协议**:
  - `REQ` 在发送消息前自动添加空分隔帧（`Empty Delimiter Frame: 0 字节`），接收回复时自动剥离空分隔帧：**已完成**
  - `REP` 接收时自动保留所有信封头（含空分隔帧），发送应答时自动将所有信封头附在应答内容前送出：**已完成**

### 5. RFC 29: PUB / SUB 套接字模式
- **订阅与广播**:
  - `PUB` 单向发送消息，支持对所有匹配该前缀的下游 Peer 进行广播：**已完成**
  - `SUB` 支持单前缀订阅与多前缀订阅：**已完成**
  - `SUB` 本地过滤机制：未订阅主题的消息在套接字层自动丢弃，不透传给应用层：**已完成**

### 6. RFC 30: PIPELINE (PUSH / PULL) 模式
- **负载分发与汇聚**:
  - `PUSH` 采用公平轮询算法（Round-Robin）将任务依次均匀投递给活跃下游：**已完成**
  - `PULL` 采用公平排队算法（Fair-Queuing）从多个上游平衡拉取数据：**已完成**
  - 单向流控约束：`PUSH` 不支持 `recv`，`PULL` 不支持 `send`：**已完成**

### 7. RFC 31 / RFC 32: ROUTER / DEALER 模式
- **路由寻址与异步通信**:
  - `ROUTER` 接收多对端消息时自动在最外层信封添加对端 `Routing-Id`：**已完成**
  - `ROUTER` 发送消息时以首帧作为目标路由凭据，将后续数据投递至指定管道：**已完成**
  - `ZMQ_ROUTER_MANDATORY` 开关支持（目标对端不存在时按配置报错）：**已完成**
  - `DEALER` 全双工自由并发收发，支持作为异步客户端与代理核心：**已完成**

### 8. RFC 47: XPUB / XSUB 模式
- **订阅透传与中继代理**:
  - `XPUB` 支持作为带有订阅感知的发布端，应用层可接收来自下游的订阅/取消指令（以 `\x01` / `\x00` 前缀表示）：**已完成**
  - `XSUB` 允许向对端双向发送订阅配置帧与数据帧，与 `XPUB` 协同可直接构建无状态高性能发布订阅中继（Broker）：**已完成**
